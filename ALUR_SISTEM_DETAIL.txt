# ALUR SISTEM POS APOTEK — DETAIL LENGKAP

================================================================================
                             ARSITEKTUR SISTEM
================================================================================

Frontend   : Next.js 14 (App Router) + TypeScript + Tailwind CSS
Backend    : Express.js 4 (Node.js) + mysql2/promise
Database   : MySQL 8+
Auth       : JWT (jsonwebtoken) + bcryptjs, dual-layer (cookie middleware + client)
Payment    : Midtrans Snap (sandbox)
Forecast   : Google Gemini API + Holt-Winters + OpenRouter
File Upload: Multer (memoryStorage → LONGBLOB MySQL)
Notifikasi : goey-toast
Icons      : lucide-react

Struktur Provider:
<html>
  <head><Script src="https://app.sandbox.midtrans.com/snap/snap.js" ... /></head>
  <body>
    <OffCanvasProvider>
      <AuthProvider>
        <HeaderProvider>
          <SidebarProvider>
            <KeyboardShortcutsProvider>
              <MainLayout>
                {children}  ← halaman yang diakses
              </MainLayout>
            </KeyboardShortcutsProvider>
          </SidebarProvider>
        </HeaderProvider>
        <GoeyToaster />
      </AuthProvider>
    </OffCanvasProvider>
  </body>
</html>

================================================================================
                     ALUR 1: AUTHENTIKASI & LOGIN
================================================================================

1. User akses halaman manapun (selain /login, /register, /forgot-password)

2. Next.js Middleware (src/middleware.ts):
   a. Baca cookie 'token'
   b. Jika tidak ada → redirect ke /login
   c. Jika ada → lanjut

3. Client-side AuthProvider (src/components/AuthProvider.tsx):
   a. Cek localStorage.getItem('token')
   b. Jika tidak ada → redirect ke /login
   c. Jika ada → render children

4. Halaman Login (src/app/login/page.tsx):
   a. Form: username, password
   b. Klik "Login"
   c. Fetch POST http://localhost:5000/api/auth/login
      - Body: { username, password }
   d. Backend:
      - Cari user di tabel users WHERE username = ? AND status = 'active'
      - Jika tidak ditemukan → 401
      - Compare password dengan bcrypt
      - Jika salah → 401
      - Jika benar:
        * Generate JWT: jwt.sign({ id: user.id, username, role }, SECRET, { expiresIn: '24h' })
        * Return 200: { token, user: { id, username, role, full_name } }
   e. Frontend:
      - Simpan token di localStorage
      - Simpan user (JSON) di localStorage
      - Set cookie 'token' = token
      - Dispatch event 'auth:changed' di window
      - Redirect ke /dashboard

5. Auto-logout (terjadi ketika):
   - API return 401 → localStorage.clear() + cookie dihapus + redirect /login
   - Token expired → middleware redirect ke /login


================================================================================
                ALUR 1b: REGISTER & FORGOT PASSWORD
================================================================================

--- REGISTER ---
1. Akses /register
2. Isi form: username, password (min 6), konfirmasi password
3. Submit → POST http://localhost:5000/api/auth/register
4. Backend:
   - Cek username unik
   - Hash password dengan bcrypt
   - INSERT ke tabel users, role default 'kasir', status 'active'
   - Return 201 { message, id }

--- FORGOT PASSWORD (4 Langkah) ---
Langkah 1: Kirim Email
   a. Akses /forgot-password, masukkan email
   b. POST /api/forgot-password → { email }
   c. Backend:
      - Generate 6-digit random code
      - Simpan di password_reset_requests (email, code hash, expires_at + 15 menit)
      - Kirim email via nodemailer (Gmail SMTP)
      - Return 200 { message }
   d. Frontend → lanjut step 2

Langkah 2: Verifikasi Kode
   a. Masukkan kode 6-digit
   b. POST /api/verify-reset-code → { email, code }
   c. Backend:
      - Cari record di password_reset_requests WHERE email AND code AND expires_at > NOW()
      - Jika cocok → set verified = true, return 200
      - Jika tidak → 400
   d. Frontend → lanjut step 3

Langkah 3: Reset Password
   a. Masukkan password baru + konfirmasi
   b. POST /api/reset-password → { email, code, new_password }
   c. Backend:
      - Verifikasi code & verified = true & belum used
      - Hash password baru
      - UPDATE users SET password = ?
      - Tandai request sebagai used
      - Return 200
   d. Frontend → lanjut step 4 (Done, link ke /login)

================================================================================
              ALUR 3: PRODUCT MANAGEMENT (HALAMAN PRODUCTS)
================================================================================

--- 3a. Melihat Daftar Produk ---
1. Akses /products
2. Frontend:
   a. Fetch GET http://localhost:5000/api/products
      - Backend query: SELECT products dengan stock_type dari batch
        menggunakan PRIORITAS (bukan batch terakhir)
        Prioritas: RETUR(1) > BELUM_BAYAR(2) > DP(3) > KONSINYASI(4) > LUNAS(5)
        Teknik: NOT EXISTS dengan FIELD() untuk cari batch prioritas tertinggi
   b. Render tabel: kode, nama, stok, kategori, harga jual, stock_type
   c. Search: input filter → set searchQuery → debounce 500ms → refetch
   d. Pagination: Show per page (10/20/50)

--- 3b. Menambah Produk Baru (Single) ---
1. Klik "Add Product" → buka OffCanvas (lebar default 400px)
2. State: showProductForm = true, productOffCanvasMode = 'add'
3. Form: nama, harga beli, harga jual, kategori, stok minimal, unit,
   unit pembelian, unit multiplier, supplier, lokasi rak, expired_date,
   gambar, catatan
4. POST /api/products (FormData — multipart, termasuk image)
5. Backend: insert ke products + audit trail, return 201

--- 3c. Menambah Banyak Produk Sekaligus (Multiple) ---
1. Toggle "Multiple Products" di form Add Product
2. Input Nomor Invoice + Upload Bukti Faktur
3. Tabel: nama produk, jumlah (unit pembelian), harga beli, harga jual,
   expired, unit multiplier — bisa tambah baris
4. Klik "Simpan Semua"
5. Backend: untuk setiap baris, cari produk by nama, insert batch baru
   dengan supplier & image dari invoice

--- 3d. Edit Produk ---
Klik edit → OffCanvas mode 'edit' → PUT /api/products/:id

--- 3e. Hapus Produk ---
ConfirmModal → DELETE /api/products/:id → set status = 'inactive' (soft delete)

--- 3f. Penentuan Stock Type Produk ---
Stock type produk ditentukan dengan prioritas (BUKAN batch terakhir):

  RETUR(1) > BELUM_BAYAR/DP/...  jika ada batch retur → produk = RETUR
  BELUM_BAYAR(2)                 jika tidak ada retur tapi ada belum_bayar
  DP(3)                          jika tidak ada retur/belum_bayar tapi ada dp
  KONSINYASI(4)                  jika tidak ada di atas tapi ada konsinyasi
  LUNAS(5)                       jika semua batch lunas

Implementasi SQL (server/routes/products.js):
  SELECT b1.product_id, b1.supplier_id, b1.stock_type
  FROM batches b1
  WHERE b1.is_archived = FALSE
    AND NOT EXISTS (
      SELECT 1 FROM batches b2
      WHERE b2.product_id = b1.product_id
        AND b2.is_archived = FALSE
        AND FIELD(b2.stock_type, 'retur', 'belum_bayar', 'dp', 'konsinyasi', 'lunas')
          < FIELD(b1.stock_type, 'retur', 'belum_bayar', 'dp', 'konsinyasi', 'lunas')
    )
  GROUP BY b1.product_id


================================================================================
              ALUR 4: MANAJEMEN FAKTUR / BATCH (DALAM PRODUCTS)
================================================================================

--- 4a. Melihat Faktur Suatu Produk ---
1. Klik baris produk → buka Faktur OffCanvas (lebar 800px)
2. Fetch GET /api/inventory/batches/:productId
3. Backend: SELECT batches + supplier_name + dp_payments + qty_returned
   (SUM dari purchase_return_items per batch)
4. Tabel: No.Faktur, Supplier, Tipe Stok, Tgl Pembelian, Status, Qty Awal,
   Qty Tersisa, Qty Terjual, **Qty Retur** (merah jika ada), Expired Date,
   Harga Beli, Total, Aksi
5. Status badge warna: approved=green, pending=yellow, rejected=red, revision=orange

--- 4b. Menambah Faktur Baru ---
1. Klik "Tambah Faktur" → form inline di OffCanvas
2. Field: nomor batch, supplier, tipe stok (belum_bayar/konsinyasi/dp/lunas —
   retur TIDAK muncul di dropdown, hanya diatur sistem), tgl beli, unit,
   jumlah, harga, expired, DP (jika tipe=dp), catatan, upload bukti
3. Klik "Tambah Faktur"
4. Backend:
   a. Hitung qtyInBaseUnit, totalAmount
   b. Approval: jika total > 2jt → status='pending', else 'approved'
   c. INSERT batch
   d. Jika dp_amount diisi → auto-create batch_dp_payments (DP 1)
   e. Jika approved → UPDATE products.stock + buat jurnal:
      - D: Persediaan (103/104) = totalAmount
      - C: Kas (101) / Hutang (201) / sesuai tipe
   f. Audit trail

--- 4c. Edit Faktur ---
1. Klik edit → form dengan data existing
2. **Validasi: jika stock_type = 'retur', tidak bisa diubah manual**
   - Backend cek: jika old.stock_type='retur' dan new≠'retur' → tolak
   - Jika new='retur' dan old≠'retur' → tolak ("hanya diatur sistem")
3. PUT /api/inventory/batches/:id
4. Backend update batches + handle stock changes + jurnal ulang

--- 4d. Hapus Faktur ---
ConfirmModal → DELETE /api/inventory/batches/:id (hard delete + cascade)

--- 4e. Manajemen DP ---
1. Ringkasan Pembayaran (mode edit & tipe DP):
   - Total Faktur, daftar DP, sisa hutang
2. Tambah DP → POST /api/inventory/batches/:batchId/dp-payments
3. Hapus DP → DELETE /api/inventory/batches/:batchId/dp-payments/:paymentId

--- 4f. Arsipkan Faktur ---
1. Tombol "Arsipkan" muncul jika stock_type = 'lunas' ATAU 'retur'
2. **Jika 'retur': validasi harus qty_returned >= initial_quantity**
   - Frontend + Backend cek: jika qty_returned < initial_quantity → tolak
     dengan pesan "Barang retur belum lengkap (X/Y)"
3. PUT /api/inventory/batches/:id/archive → { is_archived: true }
4. Backend: cek stock_type = 'lunas' atau 'retur'
   - Jika 'retur': query purchase_return_items SUM(qty_returned)
     validasi >= initial_quantity, jika tidak → error
5. UPDATE batches SET is_archived = 1

--- 4g. Upload Bukti Faktur ---
File/gambar via kamera → dikirim sebagai FormData bersama data batch

================================================================================
            ALUR 7: TRANSAKSI PENJUALAN (POS) — DENGAN FEFO!
================================================================================

--- 7a. Persiapan Transaksi ---
1. Akses /transactions
2. State: cart[], paymentMethod, amountTendered, discount, ppnRate

--- 7b. Memilih Produk ---
Search → klik → tambah ke cart → atur qty

--- 7c. FEFO (First Expired First Out) — Backend ---
POST /api/transactions:
   Untuk setiap produk:
   - SELECT batches WHERE product_id = ? AND remaining_quantity > 0
     AND is_archived = FALSE ORDER BY expired_date ASC, created_at ASC
   - Loop ambil dari batch dengan expired TERKECIL duluan
   - Simpan transaction_items per batch
   - Insert header, update remaining_quantity, update stock produk
   - **Jurnal:**
     D: Kas (101) / Piutang Midtrans
     C: Penjualan OBAT (401) / NON_OBAT (402)
     C: PPN Keluaran (202)
     D: HPP OBAT (501) / NON_OBAT (502)
     C: Persediaan OBAT (103) / NON_OBAT (104)

--- 7d. Pembayaran Tunai ---
POST /api/transactions dengan payment_method='cash' → langsung complete + jurnal

--- 7e. Pembayaran Midtrans ---
1. POST /api/transactions → payment_method='midtrans', status='pending'
2. Panggil Midtrans Snap API → return snap_token
3. Frontend: snap.pay(snap_token, ...)
4. Midtrans callback → **POST /api/midtrans/notification**
5. **Callback Midtrans — FEFO + Jurnal:**
   a. Cari transaksi by order_id
   b. Update payment_status = 'settlement'
   c. **FEFO loop: kurangi stok batch (bukan langsung products.stock)**
      - Query batch FEFO untuk tiap produk
      - Loop batch, kurangi remaining_quantity
      - Baru update products.stock total dari semua batch
   d. **Buat jurnal:**
      - Dr. Bank (102) = total_amount
      - Cr. Penjualan OBAT (401) / NON_OBAT (402)
      - Cr. PPN Keluaran (202)
      - Dr. HPP OBAT (501) / NON_OBAT (502)
      - Cr. Persediaan OBAT (103) / NON_OBAT (104)

--- 7f. Cetak Struk ---
Modal receipt → window.print()

================================================================================
            ALUR 21: RETUR PEMBELIAN (PURCHASE RETURNS)
================================================================================

--- 21a. Lookup Faktur untuk Retur ---
1. Akses /purchase-returns
2. Input nomor faktur (batch_number) → klik Cari
3. **GET /api/returns/purchases/lookup?invoice_no=XXX**
4. Backend:
   a. Cari batch WHERE batch_number = ? AND is_archived = FALSE
   b. Cari supplier, cek accepts_return
   c. Untuk tiap batch: hitung qty_already_returned (dari purchase_return_items),
      qty_returnable = initial_quantity - already_returned
   d. Return: { purchase: {id, invoice_no, date, total},
                supplier: {id, name, accepts_return, return_notes},
                items: [{batch_id, product_name, quantity, buy_price,
                         current_stock, qty_returnable, ...}] }
5. Frontend:
   - Tampilkan: supplier info, item table (produk, batch, exp, stok,
     qty_returnable, input qty retur, select kondisi)
   - Jika supplier.accepts_return = false → warning + hanya write-off
   - Summary cards: total retur, total nilai, bulan ini

--- 21b. Submit Retur Pembelian ---
1. Isi: qty retur per item, kondisi (rusak/kadaluarsa/salah_barang),
   alasan, metode penanganan
2. **Validasi Frontend:**
   - Alasan wajib diisi
   - Metode penanganan wajib dipilih
   - Qty retur harus integer 1..min(qty_returnable, current_stock)
   - Tampilkan modal konfirmasi (bukan window.confirm)
3. **POST /api/returns/purchases**
4. Backend dalam transaksi database:
   a. Validasi batch ada, stok cukup, qty tidak exceed returnable
   b. Pastikan purchase_record + purchase_item_record ada
   c. Generate return_no (RP-YYYYMMDD-XXX)
   d. INSERT purchase_returns header
   e. INSERT purchase_return_items per item
   f. **UPDATE batches: remaining_quantity = GREATEST(remaining - qty, 0)**
   g. **UPDATE batches: stock_type = 'retur'** ← otomatis!
   h. **UPDATE products: stock = GREATEST(stock - qty, 0)**
   i. Buat jurnal sesuai handling:
      - reduce_payable:  D Hutang (201), C Persediaan (103/104)
      - credit_note:      D Piutang Kredit Supplier (105), C Persediaan
      - write_off_loss:   D Beban Kerugian (528), C Persediaan
   j. Audit trail
5. Frontend: toast sukses + auto-refresh history

--- 21c. Riwayat Retur Pembelian ---
1. **GET /api/returns/purchases** → list semua retur
2. Tiap item: return_no, supplier, faktur, handling, total, tgl, reason
3. **GET /api/returns/purchases/:id** → detail + items
   Items: product_name, qty_returned, buy_price, condition

--- 21d. Dampak ke Batch ---
Setelah retur pembelian sukses:
- Stock batch berkurang (remaining_quantity -= qty_returned)
- stock_type batch BERUBAH menjadi 'retur' (otomatis oleh sistem)
- stock_type 'retur' TIDAK BISA diubah manual
- Arsip hanya bisa jika qty_returned >= initial_quantity
- Qty retur tampil MERAH di tabel detail faktur (/products)


================================================================================
            ALUR 22: RETUR PENJUALAN (SALE RETURNS)
================================================================================

--- 22a. Lookup Transaksi untuk Retur ---
1. Akses /sale-returns
2. Input ID transaksi → klik Cari
3. **GET /api/returns/sales/lookup?sale_id=XXX**
4. Backend:
   a. Cari transaksi WHERE id = ? AND payment_status = 'completed'
   b. JOIN transaction_items untuk dapat daftar produk
   c. Untuk tiap item: hitung qty_already_returned, qty_returnable
   d. Return: { sale: {id, date, total, payment_method},
                items: [{sale_item_id, product_name, quantity, price,
                         qty_returnable, ...}] }

--- 22b. Submit Retur Penjualan ---
1. Isi: qty retur per item, alasan, metode refund (cash/credit_note)
2. Validasi + modal konfirmasi
3. **POST /api/returns/sales**
4. Backend dalam transaksi database:
   a. Validasi transaksi completed, item tidak exceed qty_returnable
   b. Cari batch untuk produk:
      - Query batch non-archived (termasuk yang stok 0)
      - ORDER BY expired_date ASC, created_at ASC
      - Jika tidak ada batch → error "Tidak ditemukan batch untuk produk X"
   c. Generate return_no (RJ-YYYYMMDD-XXX)
   d. INSERT sale_returns header
   e. INSERT sale_return_items per item
   f. **UPDATE batches: remaining_quantity += qty_returned** (restore stock)
   g. **UPDATE products: stock += qty_returned**
   h. Jika semua item sudah fully returned → 
      UPDATE transactions SET is_fully_returned = TRUE
   i. Buat jurnal:
      - Dr. Retur Penjualan (403) = total_refund
      - Dr. Persediaan (103/104) = HPP
      - Cr. Kas (101) / Piutang (106) = total_refund
      - Cr. HPP OBAT (501) / NON_OBAT (502) = HPP
   j. Audit trail

--- 22c. Riwayat Retur Penjualan ---
GET /api/returns/sales → list + detail per item


================================================================================
                        CATATAN PENTING
================================================================================

1. **FEFO**: Stok batch dengan expired_date paling awal harus dijual duluan.
   Query: ORDER BY expired_date ASC, created_at ASC.
   Jangan cuma update total stock produk — harus kelola remaining_quantity
   per batch! (Berlaku untuk penjualan tunai DAN Midtrans callback)

2. **Approval**: Faktur dengan total > Rp2.000.000 otomatis pending.
   Approver harus approve dulu sebelum stok masuk.

3. **DP Payment**: Auto-create "DP 1" saat create faktur dengan tipe dp + dp_amount.
   DP berikutnya ditambahkan manual. Jurnal: D Hutang (201), C Kas/Bank (101/102).

4. **Arsip**: Hanya faktur dengan tipe 'lunas' ATAU 'retur' bisa diarsipkan.
   - 'lunas': langsung bisa arsip
   - 'retur': hanya bisa arsip jika qty_returned >= initial_quantity
     (semua barang sudah diretur lengkap)

5. **Superadmin**: Bypass permission cuma berlaku jika record permission TIDAK ADA.
   Jika record ada dengan allowed=0, superadmin pun ditolak.

6. **Jurnal Akuntansi**:
   - Pembelian: D Persediaan, K Kas/Hutang (tergantung tipe)
   - Penjualan: D Kas, K Penjualan + PPN, D HPP, K Persediaan
   - Retur Pembelian: D Hutang/Piutang/Beban, C Persediaan
   - Retur Penjualan: D ReturPenjualan + Persediaan, C Kas/Piutang + HPP
   - DP Payment: D Hutang, C Kas/Bank
   - Stock Opname: D/C Persediaan, C/D Beban Selisih Stok

7. **Retur Pembelian — stock_type menjadi 'retur'**:
   - Saat retur diproses, batch diupdate stock_type = 'retur'
   - stock_type 'retur' tidak bisa diubah manual (hanya oleh sistem)
   - Di /products, stock_type produk mengikuti prioritas (retur tertinggi)

8. **Stock Type Produk — Prioritas (bukan batch terakhir)**:
   RETUR(1) > BELUM_BAYAR(2) > DP(3) > KONSINYASI(4) > LUNAS(5)
   Implementasi: NOT EXISTS + FIELD() di products.js

9. **Supplier — Soft Delete**:
   DELETE /api/suppliers/:id → UPDATE is_deleted = TRUE
   GET selalu filter WHERE is_deleted != 1 OR IS NULL

10. **Lookup Retur Pembelian menggunakan batch_number**:
    Bukan purchases.invoice_no karena tabel purchases tidak selalu terisi.
    Batch yang lookup adalah yg is_archived = FALSE.

11. **Sale Return — Batch lookup**:
    transaction_items tidak menyimpan batch_id.
    Batch ditemukan via product_id, termasuk batch dengan remaining_quantity = 0.
    Jika tidak ada batch sama sekali → error.
