================================================================================
                     API ENDPOINTS REFERENCE (LENGKAP)
================================================================================

Semua endpoint backend berada di http://localhost:5000/api/
Kecuali dinyatakan lain, semua endpoint memerlukan header:
  Authorization: Bearer {token}

Format response sukses:  { data: ..., pagination?: {...} }
Format response error:   { message: "..." }

## A. AUTH (tidak perlu token)
------------------------------------------------------------------------

### Login
  POST /api/auth/login
  Body: { username: string, password: string }
  Response 200: { token: string, user: { id, username, role, full_name } }
  Response 401: { message: "Username atau password salah" }

### Register
  POST /api/auth/register
  Body: { username: string, password: string }
  Validasi: password >= 6 karakter
  Response 201: { message: string, id: number }

### Forgot Password (Langkah 1)
  POST /api/forgot-password
  Body: { email: string }
  Response 200: { message: string }

### Verify Reset Code (Langkah 2)
  POST /api/verify-reset-code
  Body: { email: string, code: string }
  Response 200: { message: string }

### Reset Password (Langkah 3)
  POST /api/reset-password
  Body: { email: string, code: string, new_password: string }
  Response 200: { message: string }

### Profile
  GET  /api/profile              → { data: { id, username, full_name, email, phone, role } }
  PUT  /api/profile              → Body: { full_name?, email?, phone? }
  POST /api/profile/change-password → Body: { current_password, new_password }

## B. PRODUCTS
------------------------------------------------------------------------

### List Products
  GET /api/products?page=&limit=&search=
  Response: { data: Product[], pagination: { total, page, limit, totalPages } }
  Fitur: search by name, supplier_name, location_code
    Stock type ditentukan via prioritas (retur > belum_bayar > dp > konsinyasi > lunas)
    Teknik: NOT EXISTS + FIELD() — bukan batch terakhir

### Create Product
  POST /api/products
  Body (FormData): name, cost_price, selling_price, stock, unit, expired_date,
                   location_code, supplier_id, stock_type, purchase_date,
                   invoice_number, dp_amount, due_date, purchase_unit,
                   unit_multiplier, product_category, image (file), needsApproval
  Response 201: { id: number, message: string, status?: 'pending' }

### Update Product
  PUT /api/products/:id
  Body (JSON): name, cost_price, selling_price, stock, unit, dll

### Delete Product
  DELETE /api/products/:id
  Response: { message: string }

## C. INVENTORY / BATCHES (Faktur Pembelian)
------------------------------------------------------------------------

### List Batches per Product
  GET /api/inventory/batches/:productId
  Response: { data: Batch[] } — termasuk dp_payments, qty_returned

### Create Batch
  POST /api/inventory/batches
  Body (FormData): product_id, supplier_id, batch_number, stock_type,
                   purchase_date, initial_quantity, cost_price, expired_date,
                   dp_amount, due_date, notes, image
  Jika total > 2jt → status='pending', perlu approval

### Update Batch
  PUT /api/inventory/batches/:id
  Sama seperti create. stock_type 'retur' tidak bisa diubah.

### Delete Batch
  DELETE /api/inventory/batches/:id

### Approve/Reject/Revision Batch
  PUT /api/inventory/batches/:id/approve
  PUT /api/inventory/batches/:id/reject
  PUT /api/inventory/batches/:id/revision

### Expire Batch
  PUT /api/inventory/batches/:id/expire

### Archive Batch
  PUT /api/inventory/batches/:id/archive
  Body: { is_archived: true }
  Hanya untuk stock_type 'lunas' atau 'retur' (retur harus complete)

### DP Payments
  POST   /api/inventory/batches/:batchId/dp-payments → Body: { amount, payment_date, payment_method }
  DELETE /api/inventory/batches/:batchId/dp-payments/:paymentId

### Pending Batches (for Approval page)
  GET /api/inventory/pending-batches
  Response: { data: Batch[] } — status IN ('pending','revision','rejected')

## D. TRANSACTIONS (POS)
------------------------------------------------------------------------

### Create Transaction (Cash)
  POST /api/transactions
  Body: { items: [{ product_id, quantity, selling_price }], payment_method: 'cash',
          amount_tendered, discount, tax_rate }
  Proses: FEFO (ambil batch expired terdekat duluan) + jurnal otomatis
  Response: { id, total_amount, change_amount, items_with_batches }

### Create Transaction (Midtrans)
  POST /api/transactions
  Body: { items: [...], payment_method: 'midtrans' }
  Response: { snap_token: string, order_id: string }

### Midtrans Callback
  POST /api/midtrans/notification
  Body dari Midtrans: { transaction_status, fraud_status, order_id, transaction_id, ... }
  Fitur: Idempotency (SELECT ... FOR UPDATE + cek payment_status)
         FEFO loop + jurnal dalam satu transaksi database
  Aman dari double callback

### List Transactions
  GET /api/transactions?page=&limit=&search=

### Void Transaction
  POST /api/transactions/:id/void

## E. SUPPLIERS
------------------------------------------------------------------------

  GET    /api/suppliers?page=&limit=&search=  → { data: Supplier[], pagination }
  POST   /api/suppliers                        → Body: { name, contact_person, phone, address, accepts_return, return_notes }
  GET    /api/suppliers/:id                    → Detail + batches + products
  PUT    /api/suppliers/:id                    → Update data
  DELETE /api/suppliers/:id                    → Soft delete (is_deleted = TRUE)

## F. RETUR PEMBELIAN
------------------------------------------------------------------------

  GET  /api/returns/purchases?page=&limit=              → Daftar retur
  GET  /api/returns/purchases/lookup?invoice_no=XXX     → Cari faktur untuk diretur
       Response: { purchase, supplier, items: [{batch_id, product_name, qty_returnable, ...}] }
  POST /api/returns/purchases                            → Proses retur
       Body: { items: [{batch_id, qty_returned, condition}], reason, handling }
       Efek: UPDATE batch stock_type='retur', kurangi stok, jurnal
  GET  /api/returns/purchases/:id                        → Detail retur + items

## G. RETUR PENJUALAN
------------------------------------------------------------------------

  GET  /api/returns/sales?page=&limit=                   → Daftar retur
  GET  /api/returns/sales/lookup?sale_id=XXX             → Cari transaksi
  POST /api/returns/sales                                → Proses retur
       Body: { items: [{sale_item_id, qty_returned}], reason, refund_method }
       Efek: RESTORE stok batch + jurnal
  GET  /api/returns/sales/:id                            → Detail

## H. STOCK OPNAME
------------------------------------------------------------------------

  POST /api/inventory/opname
  Body: { items: [{ product_id, batch_id, physical_stock }] }
  Efek: Hitung selisih, update remaining_quantity, jurnal selisih

  GET /api/inventory/opname/history?page=&limit=

## I. LAPORAN KEUANGAN (ACCOUNTING)
------------------------------------------------------------------------

  GET /api/reports/balance-accounting?month=&year=     → Neraca (asset=liability+equity)
  GET /api/reports/profit-loss-accounting?month=&year= → Laba/Rugi
  GET /api/reports/transactions?startDate=&endDate=    → Laporan transaksi

  GET /api/accounting/general-journal?startDate=&endDate=  → Jurnal umum
  GET /api/accounting/general-ledger?accountId=&startDate=&endDate= → Buku besar
  POST /api/accounting/journal-entries                      → Transaksi keuangan manual
       Body: { entry_date, description, items: [{account_id, debit, credit}] }

## J. RBAC (ROLE & PERMISSION)
------------------------------------------------------------------------

  GET    /api/rbac/permissions?roleId=X&roleName=Y   → Daftar permission
  PUT    /api/rbac/permissions                        → UPSERT permission
         Body: { role_id, module, action, allowed }
  POST   /api/rbac/roles                              → Tambah role
         Body: { name: string }
  DELETE /api/rbac/roles/:id                          → Hapus role (tidak bisa superadmin)

## K. SETTINGS
------------------------------------------------------------------------

  GET /api/settings               → { setting_key, setting_value }
  PUT /api/settings               → Body: { setting_key, setting_value }

## L. USERS
------------------------------------------------------------------------

  GET    /api/users               → Daftar user (tanpa password)
  POST   /api/users               → Tambah user
  PUT    /api/users/:id           → Edit user
  PUT    /api/users/:id/toggle-status → Aktif/nonaktifkan

## M. AUDIT TRAIL (READ ONLY)
------------------------------------------------------------------------

  GET /api/audit-trails?page=&limit=&module=&action=&userId=&startDate=&endDate=

## N. PRESCRIPTIONS (Resep Dokter)
------------------------------------------------------------------------

  GET    /api/prescriptions
  POST   /api/prescriptions
  PUT    /api/prescriptions/:id
  DELETE /api/prescriptions/:id

## O. STOCK FORECAST (Peramalan)

  GET /api/stock-forecast?product_id=&period=30

## Pola Umum Setiap Halaman:

  const [loading, setLoading] = useState(true);
  const [data, setData] = useState<DataType[]>([]);
  const [searchQuery, setSearchQuery] = useState('');
  const [debouncedSearchQuery, setDebouncedSearchQuery] = useState('');
  const [currentPage, setCurrentPage] = useState(1);
  const [itemsPerPage, setItemsPerPage] = useState(10);
  const [pagination, setPagination] = useState<Pagination>({...});

  // Fetch data
  const fetchData = useCallback(async () => {
    setLoading(true);
    try {
      const res = await fetch(`/api/...?page=${currentPage}&limit=${itemsPerPage}&search=${search}`);
      const json = await res.json();
      setData(json.data || []);
      setPagination(json.pagination || { total: 0, page: 1, limit: 10, totalPages: 1 });
    } catch (error) {
      console.error('Error:', error);
    } finally {
      setLoading(false);
    }
  }, [currentPage, itemsPerPage, search]);

  // Debounce search (500ms)
  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedSearchQuery(searchQuery);
      setCurrentPage(1);
    }, 500);
    return () => clearTimeout(timer);
  }, [searchQuery]);

  // Initial fetch
  useEffect(() => { fetchData(); }, [fetchData]);

================================================================================
                     ERROR HANDLING PATTERN
================================================================================

## Frontend (Global)

Setiap fetch di-catch dengan pattern:
  1. Cek res.ok
  2. Jika tidak ok → parse json error → goeyToast.error(message)
  3. Jika fetch throw (network error) → goeyToast.error('Gagal terhubung ke server')

## Backend (Global)

  app.use((err, req, res, next) => {
    console.error(err.stack);
    res.status(err.status || 500).json({ message: err.message || 'Internal Server Error' });
  });

## Pattern Khusus:

### Auto-logout (401 dari API)
  API return 401 → frontend: localStorage.clear() + cookie dihapus + redirect /login
  Implementasi: Middleware Next.js cek cookie 'token', AuthProvider cek localStorage

### Idempotency Pattern (Midtrans)
  - SELECT ... FOR UPDATE sebelum proses
  - Cek payment_status === 'completed' → skip
  - UNIQUE KEY midtrans_transaction_id
  - Update status duluan, baru FEFO + jurnal

### Permission Check
  Frontend: useRequirePermission(module) → cek 'show'
  Backend:  checkPermission(module, action) → cek role_permissions
  Superadmin bypass: hanya jika record permission TIDAK ADA (bukan allowed=0)

================================================================================
                     ALUR 1: AUTHENTIKASI & LOGIN
================================================================================

1. User akses halaman manapun (selain /login, /register, /forgot-password)

2. Next.js Middleware (src/middleware.ts):
   a. Baca cookie 'token'
   b. Jika tidak ada → redirect ke /login
   c. Jika ada → lanjut

--- 3f. Penentuan Stock Type Produk ---
Stock type produk ditentukan dengan prioritas (BUKAN batch terakhir):

  RETUR(1) > BELUM_BAYAR/DP/...  jika ada batch retur → produk = RETUR
  BELUM_BAYAR(2)                 jika tidak ada retur tapi ada belum_bayar
  DP(3)                          jika tidak ada retur/belum_bayar tapi ada dp
  KONSINYASI(4)                  jika tidak ada di atas tapi ada konsinyasi
  LUNAS(5)                       jika semua batch lunas

Implementasi SQL (server/routes/products.js):
  SELECT b1.product_id, b1.supplier_id, b1.stock_type
  FROM batches b1
  WHERE b1.is_archived = FALSE
    AND NOT EXISTS (
      SELECT 1 FROM batches b2
      WHERE b2.product_id = b1.product_id
        AND b2.is_archived = FALSE
        AND FIELD(b2.stock_type, 'retur', 'belum_bayar', 'dp', 'konsinyasi', 'lunas')
          < FIELD(b1.stock_type, 'retur', 'belum_bayar', 'dp', 'konsinyasi', 'lunas')
    )
  GROUP BY b1.product_id

--- 3g. Qty Terjual (Sold) ---
Qty Terjual dihitung sebagai NET sold (bukan gross):
  sold = initial_quantity - remaining_quantity
Ini adalah jumlah yang benar-benar sudah pergi dari stok batch saat ini.
Tidak termasuk qty yang diretur penjualan (karena stok sudah dikembalikan ke batch).

     AND is_archived = FALSE ORDER BY expired_date ASC, created_at ASC

4. Midtrans callback → **POST /api/midtrans/notification**
5. **Callback Midtrans — IDEMPOTENCY + FEFO + Jurnal:**
   a. beginTransaction() langsung (SEBELUM query apapun)
   b. SELECT ... FROM transactions WHERE midtrans_order_id = ? FOR UPDATE
      → LOCK baris, cegah race condition
   c. **Idempotency guard:** jika payment_status sudah 'completed' →
      COMMIT + return (skip, tidak proses ulang)
   d. Tentukan paymentStatus dari transaction_status & fraud_status
   e. UPDATE transactions SET payment_status = ?, midtrans_transaction_id = ?
      → Simpan transaction_id dari Midtrans (UNIQUE KEY mencegah duplikat)
   f. **FEFO loop: kurangi stok batch (bukan langsung products.stock)**
      - Query batch FEFO untuk tiap produk
      - Loop batch, kurangi remaining_quantity
      - Baru update products.stock total dari semua batch
   g. **Buat jurnal:**
      - Dr. Bank (102) = total_amount
      - Cr. Penjualan OBAT (401) / NON_OBAT (402)
      - Cr. PPN Keluaran (202)
      - Dr. HPP OBAT (501) / NON_OBAT (502)
      - Cr. Persediaan OBAT (103) / NON_OBAT (104)
   h. COMMIT

================================================================================
            ALUR 17: AUDIT TRAIL (IMMUTABLE EVENT LOG)
================================================================================

--- 17a. Arsitektur ---
Audit trail adalah append-only event log:
- INSERT-only: tidak ada UPDATE/DELETE endpoint di aplikasi
- Database trigger: BEFORE UPDATE dan BEFORE DELETE pada audit_trails
  mengeluarkan SIGNAL SQLSTATE '45000' — mencegah modifikasi dari SQL langsung
- Semua audit trail dibuat secara EVENT-DRIVEN oleh fungsi createAuditTrail()
  yang dipanggil otomatis di setiap operasi (tidak ada form manual)

--- 17b. Data yang Dicatat ---
Setiap event mencatat:
- user_id, username, role — siapa yang melakukan
- module — modul mana (Management Product, Transactions, dll)
- action — aksi (create, edit, delete, login, register, dll)
- description — deskripsi detail
- ip_address, user_agent — dari request header (jika tersedia)
- created_at — timestamp otomatis

--- 17c. API ---
GET /api/audit-trails?page=&limit=&module=&action=&userId=&startDate=&endDate=
Filter + pagination, ORDER BY created_at DESC
Hanya read-only, tidak ada POST/PUT/DELETE

--- 17d. Event-Driven — Semua Modul ---
createAuditTrail() di-inject ke setiap route handler sebagai callback:
  registerUserRoutes, registerProductRoutes, registerTransactionRoutes,
  registerSupplierRoutes, registerInventoryRoutes, registerReturnRoutes,
  registerProfileRoutes, registerSettingsRoutes
Ditambah inline di index.js untuk register + login

Tidak ada cara untuk membuat audit trail secara manual — hanya terjadi
saat aksi nyata di sistem.

            ALUR 21: RETUR PEMBELIAN (PURCHASE RETURNS)
================================================================================

--- 21a. Lookup Faktur untuk Retur ---
1. Akses /purchase-returns
2. Input nomor faktur (batch_number) → klik Cari
3. **GET /api/returns/purchases/lookup?invoice_no=XXX**
4. Backend:
   a. Cari batch WHERE batch_number = ? AND is_archived = FALSE
   b. Cari supplier, cek accepts_return
   c. Untuk tiap batch: hitung qty_already_returned (dari purchase_return_items),
      qty_returnable = initial_quantity - already_returned
   d. Return: { purchase: {id, invoice_no, date, total},
                supplier: {id, name, accepts_return, return_notes},
                items: [{batch_id, product_name, quantity, buy_price,
                         current_stock, qty_returnable, ...}] }
5. Frontend:
   - Tampilkan: supplier info, item table (produk, batch, exp, stok,
     qty_returnable, input qty retur, select kondisi)
   - Jika supplier.accepts_return = false → warning + hanya write-off
   - Summary cards: total retur, total nilai, bulan ini

--- 21b. Submit Retur Pembelian ---
1. Isi: qty retur per item, kondisi (rusak/kadaluarsa/salah_barang),
   alasan, metode penanganan
2. **Validasi Frontend:**
   - Alasan wajib diisi
   - Metode penanganan wajib dipilih
   - Qty retur harus integer 1..min(qty_returnable, current_stock)
   - Tampilkan modal konfirmasi (bukan window.confirm)
3. **POST /api/returns/purchases**
4. Backend dalam transaksi database:
   a. Validasi batch ada, stok cukup, qty tidak exceed returnable
   b. Pastikan purchase_record + purchase_item_record ada
   c. Generate return_no (RP-YYYYMMDD-XXX)
   d. INSERT purchase_returns header
   e. INSERT purchase_return_items per item
   f. **UPDATE batches: remaining_quantity = GREATEST(remaining - qty, 0)**
   g. **UPDATE batches: stock_type = 'retur'** ← otomatis!
   h. **UPDATE products: stock = GREATEST(stock - qty, 0)**
   i. Buat jurnal sesuai handling:
      - reduce_payable:  D Hutang (201), C Persediaan (103/104)
      - credit_note:      D Piutang Kredit Supplier (105), C Persediaan
      - write_off_loss:   D Beban Kerugian (528), C Persediaan
   j. Audit trail
5. Frontend: toast sukses + auto-refresh history

--- 21c. Riwayat Retur Pembelian ---
1. **GET /api/returns/purchases** → list semua retur
2. Tiap item: return_no, supplier, faktur, handling, total, tgl, reason
3. **GET /api/returns/purchases/:id** → detail + items
   Items: product_name, qty_returned, buy_price, condition

--- 21d. Dampak ke Batch ---
Setelah retur pembelian sukses:
- Stock batch berkurang (remaining_quantity -= qty_returned)
- stock_type batch BERUBAH menjadi 'retur' (otomatis oleh sistem)
- stock_type 'retur' TIDAK BISA diubah manual
- Arsip hanya bisa jika qty_returned >= initial_quantity
- Qty retur tampil MERAH di tabel detail faktur (/products)
- Batch endpoint juga mengembalikan qty_restored (dari sale_return_items)
  untuk informasi, tidak dipakai dalam perhitungan sold


================================================================================
            ALUR 22: RETUR PENJUALAN (SALE RETURNS)
================================================================================

--- 22a. Lookup Transaksi untuk Retur ---
1. Akses /sale-returns
2. Input ID transaksi → klik Cari
3. **GET /api/returns/sales/lookup?sale_id=XXX**
4. Backend:
   a. Cari transaksi WHERE id = ? AND payment_status = 'completed'
   b. JOIN transaction_items untuk dapat daftar produk
   c. Untuk tiap item: hitung qty_already_returned, qty_returnable
   d. Return: { sale: {id, date, total, payment_method},
                items: [{sale_item_id, product_name, quantity, price,
                         qty_returnable, ...}] }

--- 22b. Submit Retur Penjualan ---
1. Isi: qty retur per item, alasan, metode refund (cash/credit_note)
2. Validasi + modal konfirmasi
3. **POST /api/returns/sales**
4. Backend dalam transaksi database:
   a. Validasi transaksi completed, item tidak exceed qty_returnable
   b. Cari batch untuk produk:
      - Query batch non-archived (termasuk yang stok 0)
      - ORDER BY expired_date ASC, created_at ASC
      - Jika tidak ada batch → error "Tidak ditemukan batch untuk produk X"
   c. Generate return_no (RJ-YYYYMMDD-XXX)
   d. INSERT sale_returns header
   e. INSERT sale_return_items per item
   f. **UPDATE batches: remaining_quantity += qty_returned** (restore stock)
   g. **UPDATE products: stock += qty_returned**
   h. Jika semua item sudah fully returned → 
      UPDATE transactions SET is_fully_returned = TRUE
   i. Buat jurnal:
      - Dr. Retur Penjualan (403) = total_refund
      - Dr. Persediaan (103/104) = HPP
      - Cr. Kas (101) / Piutang (106) = total_refund
      - Cr. HPP OBAT (501) / NON_OBAT (502) = HPP
   j. Audit trail

--- 22c. Riwayat Retur Penjualan ---
GET /api/returns/sales → list + detail per item


================================================================================
                        CATATAN PENTING
================================================================================

1. **FEFO**: Stok batch dengan expired_date paling awal harus dijual duluan.
   Query: ORDER BY expired_date ASC, created_at ASC.
   Jangan cuma update total stock produk — harus kelola remaining_quantity
   per batch! (Berlaku untuk penjualan tunai DAN Midtrans callback)

2. **Approval**: Faktur dengan total > Rp2.000.000 otomatis pending.
   Approver harus approve dulu sebelum stok masuk.

3. **DP Payment**: Auto-create "DP 1" saat create faktur dengan tipe dp + dp_amount.
   DP berikutnya ditambahkan manual. Jurnal: D Hutang (201), C Kas/Bank (101/102).

4. **Arsip**: Hanya faktur dengan tipe 'lunas' ATAU 'retur' bisa diarsipkan.
   - 'lunas': langsung bisa arsip
   - 'retur': hanya bisa arsip jika qty_returned >= initial_quantity
     (semua barang sudah diretur lengkap)

5. **Superadmin**: Bypass permission cuma berlaku jika record permission TIDAK ADA.
   Jika record ada dengan allowed=0, superadmin pun ditolak.

6. **Jurnal Akuntansi**:
   - Pembelian: D Persediaan, K Kas/Hutang (tergantung tipe)
   - Penjualan: D Kas, K Penjualan + PPN, D HPP, K Persediaan
   - Retur Pembelian: D Hutang/Piutang/Beban, C Persediaan
   - Retur Penjualan: D ReturPenjualan + Persediaan, C Kas/Piutang + HPP
   - DP Payment: D Hutang, C Kas/Bank
   - Stock Opname: D/C Persediaan, C/D Beban Selisih Stok

7. **Retur Pembelian — stock_type menjadi 'retur'**:
   - Saat retur diproses, batch diupdate stock_type = 'retur'
   - stock_type 'retur' tidak bisa diubah manual (hanya oleh sistem)
   - Di /products, stock_type produk mengikuti prioritas (retur tertinggi)

8. **Stock Type Produk — Prioritas (bukan batch terakhir)**:
   RETUR(1) > BELUM_BAYAR(2) > DP(3) > KONSINYASI(4) > LUNAS(5)
   Implementasi: NOT EXISTS + FIELD() di products.js

9. **Supplier — Soft Delete**:
   DELETE /api/suppliers/:id → UPDATE is_deleted = TRUE
   GET selalu filter WHERE is_deleted != 1 OR IS NULL

10. **Lookup Retur Pembelian menggunakan batch_number**:
    Bukan purchases.invoice_no karena tabel purchases tidak selalu terisi.
    Batch yang lookup adalah yg is_archived = FALSE.

11. **Sale Return — Batch lookup**:
    transaction_items tidak menyimpan batch_id.
    Batch ditemukan via product_id, termasuk batch dengan remaining_quantity = 0.
    Jika tidak ada batch sama sekali → error.

12. **Midtrans Callback — Idempotency (cegah FEFO double)**:
    Dua layer pengaman:
    a. Database UNIQUE KEY pada midtrans_transaction_id → mencegah duplikat
       secara skema walau order_id berbeda
    b. SELECT ... FOR UPDATE + state lock pattern:
       - beginTransaction() sebelum SELECT
       - FOR UPDATE lock baris transaksi
       - Cek payment_status === 'completed' → jika sudah, skip
       - Update payment_status duluan SEBELUM FEFO/jurnal
       - Callback kedua akan lihat status 'completed' dan berhenti
    Ini mencegah skenario: callback masuk 2x → FEFO jalan 2x → stok dobel minus

13. **Audit Trail — Immutable (append-only)**:
    a. Aplikasi: tidak ada endpoint PUT/DELETE untuk audit_trails
    b. Database: trigger BEFORE UPDATE dan BEFORE DELETE pada tabel
       audit_trails → SIGNAL SQLSTATE '45000' (error)
    c. Semua audit trail dibuat event-driven oleh createAuditTrail()
       callback — tidak ada form manual
    d. Setiap event mencatat: user_id, username, role, module, action,
       description, ip_address, user_agent

14. **Sold Quantity — Net Calculation**:
    Qty Terjual = initial_quantity - remaining_quantity (NET sold)
    Tidak termasuk qty yang dikembalikan via sale return (karena stok
    sudah direstore ke batch). Ini berbeda dari gross sold yang
    menghitung total penjualan kotor.

15. **RBAC Modules — System Settings dipecah**:
    Module `System Settings` (lama) dipecah menjadi 2 module terpisah:
    - `Role & Permission`: manage role + permission toggles (create/edit/delete/show)
    - `Transaction Setting`: manage PPN rate & diskon (show/edit)
    Masing-masing memiliki permission sendiri dan superadmin bypass.
    Sidebar: System Settings sebagai parent dropdown, visibility
    menggunakan OR dari kedua module.
